# Feature Specification: 위젯 회사별 사규 문서 RAG

**Feature Branch**: `feature/skill-modify-hrchat-merge` (스펙 디렉토리 `specs/021-widget-company-docs-rag`)

**Created**: 2026-11-10

**Status**: Draft

**Input**: User description: "고객사의 취업규칙과 사규 등을 검색해 답변에 활용하는 RAG 기능을 위젯 AI에 반영. 채팅봇에서 고객 회사별로 파일을 넣을 수 있도록 — 기존 teamplgpt workspace에서 등록한 파일 + 위젯에서 등록한 파일." → 업로드는 위젯을 쓰는 직원 누구나, 같은 회사끼리 공유, 같은 회사 직원 누구나 삭제, 충돌 시 회사 문서 우선, 답변에 출처 표시 없음, TeamplGPT 업로드 가능 형식 전부 + HWP.

**Convention**: HR agent-skill 7종의 `plugin.json` description을 바꾸지 않는다 → `docs/conventions/hr-skill-description-pattern.md` 적용 대상 아님(T-A/T-B 해당 없음).

**관련 저장소**: TeamplGPT(이 저장소) + okrservice(`/Users/shin-yeji/okrservice`, 위젯 화면 `widgets/client/messenger/components/chatbot/`·위젯 서버 프록시 `widgets/server/index.ts`).

## 배경

고객사 임직원은 휴가·경조사·복리후생 같은 회사 제도를 인사팀에 전화나 메일로 반복해서 묻는다. 위젯 AI가 그 회사의 취업규칙·사규를 근거로 1차 안내를 하면 인사팀 문의가 줄어든다.

현재 상태(2026-11-10 확인):

- 위젯 채팅은 TeamplGPT embed 경로(`/api/embed/:embedId/stream-chat`)를 쓴다. okrservice 위젯 서버가 환경변수의 embed ID **하나**로 모든 고객사 요청을 보내며, 보내는 값은 `message`·`sessionId`뿐이다. TeamplGPT는 어느 회사 직원인지 모른다.
- embed 채팅은 질문마다 그 워크스페이스 문서(+ 공유 워크스페이스 문서)를 벡터 검색해 답변에 쓴다. 회사별 문서 구분은 없다.
- 문서 업로드는 TeamplGPT 관리자 화면(로그인한 admin/manager)에서만 된다. 위젯에는 업로드 경로가 없다.
- 위젯 연결 시 고객사 페이지가 `erxesSettings.messenger.companyData = { name: '오이사공' }`을 넘기면, erxes 서버가 그 이름으로 회사(Company)를 찾거나 만들고 직원(customer)을 그 회사에 연결한다. 다만 연결 응답에 회사 ID는 돌려주지 않는다. 위젯이 확실히 아는 회사 정보는 `companyData.name`뿐이다.
- 위젯은 답변의 출처(sources)를 지금도 표시하지 않는다.
- TeamplGPT 문서 변환기는 HWP를 지원하지 않는다. `.doc`(구형 워드)도 지원하지 않는다(`.docx`만).

| D15 | 파일 크기 상한 | 파일 하나 50MB | 내 판단. 취업규칙 PDF는 보통 수 MB. 음성·영상은 이 상한 안에서만 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회사 취업규칙을 근거로 답을 받는다 (Priority: P1)

A사 직원이 위젯에서 "경조휴가 며칠이야?"라고 묻는다. A사 직원이 올려 둔 취업규칙에 "본인 결혼 5일"이 있다. 챗봇은 그 내용을 근거로 "본인 결혼 시 경조휴가는 5일입니다"처럼 답한다. 출처 표시는 없다.

**Why this priority**: 기능의 존재 이유. 문서가 이미 올라가 있다면 이것만으로 인사팀 문의를 줄인다.

**Independent Test**: A사 문서 공간에 테스트 취업규칙을 미리 넣어 두고 A사 직원으로 질문한다. 답변에 문서 내용이 반영되면 된다.

**Acceptance Scenarios**:

1. **Given** A사 취업규칙(경조휴가 본인 결혼 5일)이 A사 문서로 등록됨, **When** A사 직원이 "결혼하면 휴가 며칠?", **Then** 5일이라고 답하고 출처 문서 이름은 표시하지 않는다.
2. **Given** 공통 문서에 "경조휴가 3일", A사 문서에 "5일", **When** A사 직원이 같은 질문, **Then** 5일로 답한다(회사 문서 우선).
3. **Given** 같은 상태, **When** B사 직원(회사 문서 없음)이 같은 질문, **Then** 공통 문서 기준 3일로 답하고 A사 문서 내용은 나오지 않는다.
4. **Given** A사 문서에도 공통 문서에도 관련 내용이 없음, **When** A사 직원이 질문, **Then** 지어내지 않고 확인할 수 없다는 취지로 답하고 인사팀 문의를 안내한다.

---

### User Story 2 - 직원이 위젯에서 회사 문서를 올린다 (Priority: P1)

A사 직원이 위젯 챗봇의 "우리 회사 문서" 화면에서 취업규칙 PDF(또는 HWP)를 고른다. 업로드 후 목록에 "처리 중"으로 보이고, 처리가 끝나면 "사용 가능"으로 바뀐다. 그때부터 A사 직원 누구의 질문에도 이 문서가 쓰인다.

**Why this priority**: 운영자 개입 없이 고객사가 스스로 문서를 넣는 것이 요청의 핵심.

**Independent Test**: A사 직원으로 PDF 한 개를 올린 뒤, 다른 A사 직원 세션에서 그 문서 내용을 묻는다.

**Acceptance Scenarios**:

1. **Given** A사 직원, **When** 취업규칙.pdf를 올림, **Then** 목록에 파일 이름·올린 사람·날짜·"처리 중"이 보이고, 처리가 끝나면 "사용 가능"이 된다.
2. **Given** 처리 완료, **When** 다른 A사 직원이 내용을 질문, **Then** 그 내용으로 답한다.
3. **Given** 처리 완료, **When** B사 직원이 위젯 문서 목록을 열거나 같은 내용을 질문, **Then** 목록에 A사 문서가 없고 답변에도 A사 문서 내용이 쓰이지 않는다.
4. **Given** A사 직원, **When** 사규.hwp(또는 .hwpx)를 올림, **Then** PDF와 같은 흐름으로 처리돼 질문에 쓰인다.
5. **Given** A사 직원, **When** 허용되지 않는 형식(.doc, .zip 등)이나 50MB 초과 파일을 고름, **Then** 올리지 않고 이유(형식 미지원 / 크기 초과)를 알려 준다.
6. **Given** 변환에 실패한 파일(암호 걸린 PDF, 손상 파일 등), **When** 처리 완료, **Then** 목록에 "실패"로 보이고 답변에는 쓰이지 않으며, 직원이 지울 수 있다.

### User Story 3 - 잘못 올린 문서를 같은 회사 직원이 지운다 (Priority: P1)

A사 직원 김씨가 작년 취업규칙을 올렸다. 동료 이씨가 목록에서 올린 사람과 날짜를 보고 그 파일을 지운다. 지운 직후부터 A사 답변에서 그 내용이 빠진다.

**Why this priority**: 누구나 올릴 수 있는 구조(D1)에서 잘못된 안내가 퍼지는 것을 막는 유일한 수단(D3).

**Independent Test**: A사 문서 하나를 다른 A사 직원 세션에서 삭제한 뒤 그 문서에만 있던 내용을 질문한다.

**Acceptance Scenarios**:

1. **Given** 김씨가 올린 A사 문서, **When** 이씨(A사)가 목록에서 삭제를 누르고 확인, **Then** 목록에서 사라지고 이후 A사 질문 답변에 그 내용이 쓰이지 않는다.
2. **Given** A사 문서, **When** B사 직원이 그 문서를 지우려 시도(직접 요청 포함), **Then** 거부된다.
3. **Given** 워크스페이스 공통 문서, **When** 위젯 직원 누구든, **Then** 목록에 보이지 않고 지울 수 없다.

---

### User Story 4 - 기존 TeamplGPT 화면에서 HWP를 올린다 (Priority: P3)

TeamplGPT 운영자가 관리자 화면 워크스페이스에 HWP 공통 문서를 올리면 다른 형식과 같이 처리된다(D11 부수 효과).

**Why this priority**: 요청의 직접 대상은 아니지만 변환기 공통 추가로 함께 생긴다.

**Independent Test**: 관리자 화면에서 HWP 업로드 → 워크스페이스에 임베딩 → 내용 질문.

**Acceptance Scenarios**:

1. **Given** 관리자, **When** 워크스페이스에 .hwp 업로드, **Then** 문서로 처리되고 질문에 쓰인다.

### Edge Cases

- 회사 정보 없는 직원(D6): 문서 화면이 보이지 않고, 업로드·목록·삭제 요청이 직접 와도 거부한다. 채팅은 공통 문서만으로 답한다.
- 워크스페이스에 공통 문서가 하나도 없고 회사 문서만 있는 경우: 회사 문서만으로 정상 답변한다(현재 "문서 없으면 답변 거부" 분기가 회사 문서를 고려해야 함).
- 회사 문서 공간 검색이 실패한 경우: 채팅 전체를 실패시키지 않고 공통 문서만으로 답한다(기존 공유 워크스페이스 실패 처리와 같은 원칙).
- 처리 중에 삭제한 경우: 처리가 끝나도 검색 공간에 남지 않는다.
- 같은 이름 파일 재업로드(D14): 두 문서가 모두 목록에 남는다.
- 큰 문서 여러 개를 동시에 올리는 경우: 각각 독립적으로 처리되고 하나의 실패가 다른 파일을 막지 않는다.
- 회사 문서 내용이 질문과 무관한 경우: 회사 문서라는 이유만으로 억지로 끼워 넣지 않는다.
- HR 조회 질문("이번 달 근무현황")에는 기존 HR 스킬 동작이 그대로 유지된다. 회사 문서 검색이 HR 스킬 답변을 바꾸지 않는다.
- 회사 문서 안에 "이전 지시를 무시하라" 같은 문장이 있는 경우: 문서 내용은 참고 자료로만 쓰이고 지시로 따르지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**회사 식별**

- **FR-001**: 위젯 채팅·문서 요청은 그 위젯 화면의 회사 구분 값(`companyData.name`, D4)을 TeamplGPT까지 전달해야 한다.
- **FR-002**: 회사 구분 값이 없거나 공백뿐이면 회사 문서 기능을 비활성화하고(D6), 채팅은 기존과 같이 동작해야 한다.

**문서 관리**

- **FR-003**: 직원은 위젯에서 D10 형식의 파일을 하나 이상 올릴 수 있어야 하며, 파일 하나당 50MB를 넘으면 거부되어야 한다.
- **FR-004**: 올린 문서는 그 회사 전용 검색 공간에만 저장되어야 한다(D17).
- **FR-005**: 직원은 자기 회사 문서 목록을 볼 수 있어야 하며, 각 문서에 파일 이름·올린 사람·올린 날짜·처리 상태가 보여야 한다(D13).
- **FR-006**: 같은 회사 직원은 누구나 그 회사 문서를 삭제할 수 있어야 하며, 삭제 즉시 이후 답변의 검색 대상에서 빠져야 한다.
- **FR-007**: 다른 회사 문서의 목록 조회·삭제·검색은 어떤 경로로도 불가해야 한다(요청에 다른 문서 ID를 직접 넣어도 거부).
- **FR-008**: 워크스페이스 공통 문서는 위젯 목록에 나오지 않고 위젯에서 삭제할 수 없어야 한다(D12).
- **FR-009**: 변환 실패 문서는 "실패" 상태로 남아 검색에 쓰이지 않고 삭제 가능해야 한다.

**답변**

- **FR-010**: embed 채팅은 공통 문서 검색 결과와 그 직원 회사 문서 검색 결과를 함께 답변 근거로 써야 한다(D7).
- **FR-011**: 둘이 충돌하면 회사 문서 기준으로 답해야 한다(D8). 이 규칙은 프롬프트 지시(L1)와 근거 구성 단계의 회사 문서 구분·우선 배치(L2)로 이중 보장하고 E2E 시나리오(L3)로 검증한다.
- **FR-012**: 답변에 출처 문서 이름·조항을 표시하지 않는다(D9, 현재 위젯 동작 유지).
- **FR-013**: 회사 문서 검색 실패 시 공통 문서만으로 답해야 한다.
- **FR-014**: 기존 HR 스킬 답변, 공유 워크스페이스 병합, 웹 채팅·@agent 동작은 바뀌지 않아야 한다(D18).

**형식**

- **FR-015**: 문서 변환기가 HWP·HWPX에서 본문과 표의 텍스트를 추출해야 한다. 이 변환기는 기존 워크스페이스 업로드에도 적용된다(D11).

**UI**

- **FR-016**: 위젯 문서 화면의 문자열은 한국어·영어를 함께 제공해야 한다.

### Key Entities

- **회사(Company)**: 고객사. 위젯이 넘기는 회사 이름(앞뒤 공백 제거)으로 식별한다. TeamplGPT는 이 값을 문서 공간을 나누는 데만 쓴다.
- **회사 문서(Company Document)**: 위젯에서 올린 파일 하나. 속성: 소속 회사 구분 값, 소속 embed(워크스페이스), 파일 이름, 올린 사람 표시명, 올린 시각, 처리 상태(처리 중/사용 가능/실패).
- **회사 문서 공간(Company Document Space)**: 한 워크스페이스 × 한 회사의 검색 공간. 공통 문서 공간·다른 회사 공간과 분리.
- **공통 문서(Workspace Document)**: 기존 TeamplGPT 관리자 화면에서 올린 워크스페이스 문서. 변경 없음.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 회사 문서에만 있는 규정을 묻는 테스트 질문 10건 중 9건 이상에서 그 규정 내용으로 답한다.
- **SC-002**: 공통 문서와 회사 문서가 충돌하는 테스트 질문 전부에서 회사 문서 기준으로 답한다.
- **SC-003**: 다른 회사 직원 세션에서 A사 전용 내용을 묻는 테스트 질문 전부에서 A사 문서 내용이 답변에 나오지 않는다(누출 0건).
- **SC-004**: 10MB 이하 PDF·HWP 문서는 업로드 후 2분 안에 "사용 가능"이 된다.
- **SC-005**: 문서 삭제 후 다음 질문부터 그 문서 내용이 답변에 쓰이지 않는다.
- **SC-006**: 기존 HR E2E 시나리오와 embed E2E 시나리오가 전건 PASS(회귀 없음).
- **SC-007**: 직원이 설명 없이 문서 올리기 → 목록 확인 → 삭제를 3분 안에 마칠 수 있다.

## Assumptions

- 고객사 페이지는 `erxesSettings.messenger.companyData.name`에 회사마다 항상 같은 표기로 회사 이름을 넣는다. 표기가 바뀌면 문서가 다른 회사 공간으로 갈라진다(D4 한계). 넣지 않은 고객사는 D6로 동작한다.
- 회사 이름은 저장·검색 공간 이름에 그대로 쓰지 않고, 한글·특수문자를 안전하게 다룰 수 있는 형태로 변환해 쓴다(방식은 plan에서 결정).
- 업로드한 사람 표시는 위젯이 이미 아는 직원 이름 또는 이메일(`erxesSettings.messenger.email`)을 쓴다.
- 모든 고객사가 지금처럼 같은 embed(같은 워크스페이스)를 공유한다. 회사별 embed 분리는 하지 않는다.
- 회사 문서의 보관 기간은 직원이 지울 때까지(자동 만료 없음).
- 회사별 문서 개수·총용량 제한은 1차에 두지 않는다.
- HWP 변환은 서버에서 동작하는 오픈소스 라이브러리로 가능하다고 가정한다. 표·이미지가 많은 문서에서 추출 품질은 plan 단계에서 실제 샘플로 확인한다.
- 위조 위험(D5)을 서버 검증으로 막는 작업은 후속 과제다.

## Out of Scope

- `.doc`(구형 워드) 지원
- 답변 출처 표시
- 회사별 관리자 역할, 업로드 승인 절차
- 회사 위조 방지(서버 측 회사 검증)
- 웹 채팅·@agent에서 회사 문서 검색
- TeamplGPT 관리자 화면에서 회사 문서 조회·관리
