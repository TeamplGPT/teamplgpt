# Feature Specification: 위젯 챗봇 급여명세서를 5240 급여명세서 화면 구성으로

**Feature Branch**: `feature/skill-modify-hrchat-merge` (스펙 디렉토리 `specs/024-payslip-5240-layout`)

**Created**: 2026-11-18

**Status**: Draft

**Input**: User description: "위젯 챗봇에서 '급여명세서 보여줘'라고 하면 5240 급여명세서 화면과 같은 구성으로 답한다. 기존 급여명세서 조회 하나가 5240 조회 4개를 불러 한 답으로 묶는다(합계·지급내역·공제내역·기재사항)."

**Convention**: `hr-salary` `plugin.json`의 query_type 설명(Location B)을 바꾼다 → `docs/conventions/hr-skill-description-pattern.md` 적용. 새 주기 파라미터·새 query_type은 없으므로 T-A/T-B 템플릿은 해당 없음. §4.3(hr-salary 2단계 예외)을 유지하고 §7.3 회귀 검증 절차(케이스 먼저 → FAIL 확인 → 수정 → 경계 재검증 → 전체 2회 연속)를 따른다.

**관련 저장소**: TeamplGPT(이 저장소 — `hr-salary` skill, 라우팅 평가, E2E)와 okrservice(위젯 브리지 허용 목록 `widgets/client/messenger/widget/hrBridge.ts`). kiwibox(5240)는 읽기 전용이라 수정하지 않는다.

## 배경

직원이 위젯 챗봇에 "급여명세서 보여줘"라고 물으면, 지금은 **지급 항목 표 하나**만 나온다. 이 표에는 5240 화면이 숨기는 지급구분·급여연월 칸이 보이고, 공제내역·합계·기재사항은 따로 물어야 나온다(2026-11-18 로컬 확인, 가짜 데이터).

5240 급여명세서 화면(SAL-0220 직원 셀프서비스·SAL-0230 본인만, kiwibox `salSalaryDtstmnMgr`)은 한 화면에 아래를 함께 보여준다. 데이터가 없을 때 사용자가 본 화면(2026-11-18):

```
지급금액 0 / 공제금액 0 / 실지급액 0
기재사항 — 기재구분 · 기재항목 · 금액/시간등
지급내역 0건 — 지급항목 · 지급금액 · 합계
공제내역 0건 — 공제항목 · 공제금액 · 합계
```

화면 각 영역의 데이터 출처(kiwibox `SALSalaryDtstmnMgr_SQL.xml`, spec-docs `salSalaryDtstmnMgr.md`):

| 영역 | 보여주는 칸 | 5240 조회 | 챗봇 현황 |
|---|---|---|---|
| 합계 | 지급금액 · 공제금액 · 실지급액 | `getSALSalaryDtstmnMgrMap` (JTOT/GTOT/CTOT) | 있음(실수령 질문에만 사용) |
| 지급내역 | 지급항목 · 지급금액, 소급금액(합이 0이면 숨김) | `getSALSalaryDtstmnMgrList` (지급, SAL_ITEM_TYPE_CD='J') | 있음(지급구분·급여연월까지 노출) |
| 공제내역 | 공제항목 · 공제금액 | `getSALSalaryDtstmnMgrList2` (공제, 'G') | 있음(공제 질문에만 사용) |
| 기재사항 | 기재구분(E=기준항목, T=근태항목) · 기재항목 · 금액/시간등 | `getSALSalaryDtstmnMgrList3` (기재, 'C') | **없음**. 위젯 브리지도 막혀 있다 |

네 조회는 모두 같은 지급 건 코드(급여일자+유형)와 본인 사번을 받는다. 지급구분·적용년월 칸은 5240 화면에서 숨김이고, 고지사항은 HTML로 따로 온다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 급여명세서를 물으면 5240 화면과 같은 구성으로 본다 (Priority: P1)

직원이 위젯에서 "10월 급여명세서 보여줘"라고 묻는다. 챗봇이 한 답 안에 실지급액 한 줄, 지급금액·공제금액·실지급액 합계, 지급내역(항목별 금액과 합계), 공제내역(항목별 금액과 합계), 기재사항을 보여준다. 직원은 5240에 로그인하지 않고도 같은 정보를 확인한다.

**Why this priority**: 이 기능의 목적 그 자체다. 지금은 지급 항목만 보여 "명세서"라 부르기 어렵다.

**Independent Test**: 지급 4건·공제 6건·기재 2건이 있는 가짜 지급 건으로 "10월 급여명세서 보여줘"를 물어, 답에 네 영역이 D3 순서로 있고 금액이 5240 응답과 같은지 본다.

**Acceptance Scenarios**:

1. **Given** 10월 지급 건에 지급 4건(합 3,450,000)·공제 6건(합 386,210)·기재 2건이 있다, **When** "10월 급여명세서 보여줘", **Then** 합계 표에 지급금액 3,450,000·공제금액 386,210·실지급액 3,063,790이, 지급내역·공제내역 표에 항목과 합계 줄이, 기재사항 표에 기재구분(기준항목/근태항목)·기재항목·금액/시간등이 나온다.
2. **Given** 같은 지급 건, **When** 답을 본다, **Then** 지급구분·급여연월 칸이 어느 표에도 없다.
3. **Given** 소급금액이 모두 0인 지급 건, **When** 명세서를 본다, **Then** 지급내역 표에 소급금액 칸이 없다. **Given** 소급금액이 있는 항목이 하나라도 있다, **Then** 소급금액 칸이 보인다.
4. **Given** 기재사항이 0건인 지급 건(예: 상여), **When** 명세서를 본다, **Then** 기재사항 표는 나오지 않고 나머지 영역은 그대로 나온다.
5. **Given** "페이슬립 보여줘", "월급 명세서 줘"처럼 다른 말로 묻는다, **Then** 같은 네 영역 구성으로 답한다.

---

### User Story 2 - 공제만·실수령만 물으면 그 부분만 본다 (Priority: P1)

직원이 "10월에 얼마 떼갔어?"라고 물으면 공제내역만, "10월 실수령 얼마야?"라고 물으면 합계만 본다. 명세서 전체가 쏟아지지 않는다.

**Why this priority**: D2. 명세서 묶음이 다른 급여 질문의 답까지 길게 만들면 안 된다(회귀 방지).

**Independent Test**: 같은 가짜 지급 건으로 두 질문을 물어 각각 공제내역 표만, 합계 표만 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 10월 지급 건, **When** "10월에 얼마 떼갔어?", **Then** 공제내역(공제항목·공제금액)만 나오고 지급내역·기재사항은 없다.
2. **Given** 10월 지급 건, **When** "10월 실수령 얼마야?", **Then** 첫 문장에 실지급액 3,063,790원이 나오고, 지급·공제 항목 표는 없다.

---

### User Story 3 - 이번 달이 아직이면 지난달 명세서를 같은 구성으로 본다 (Priority: P2)

11월 18일에 "이번 달 급여명세서 보여줘"라고 물으면, 11월 급여가 아직 지급 전이므로 첫 문장에서 그 사실을 밝히고 10월 명세서를 같은 네 영역 구성으로 보여준다.

**Why this priority**: D9. 기존 규칙과 새 구성이 함께 동작하는지 확인한다.

**Independent Test**: 11월 지급 건이 없는 가짜 데이터로 "이번 달 급여명세서 보여줘"를 묻는다.

**Acceptance Scenarios**:

1. **Given** 11월 지급 건 없음·10월 있음, **When** "이번 달 급여명세서 보여줘", **Then** 첫 문장이 "이번 달 급여는 아직 지급 전이라 지난달(10월) 기준"임을 밝히고, 10월 명세서가 네 영역 구성으로 나온다.

---

### Edge Cases

- **기재사항 조회 실패**(위젯 브리지가 아직 배포 전이라 막힘 등): 기재사항 자리에 "기재사항은 조회하지 못했어요"를 표시하고 나머지 세 영역은 보여준다(D7).
- **합계 조회 실패**: 합계 표 자리에 조회 실패를 표시한다. 지급·공제 표의 합계 줄로 실지급액을 계산해 대신 말하지 않는다.
- **지급내역·공제내역이 모두 0건인 지급 건**: 5240 화면처럼 "0건"으로 보여주고 지어내지 않는다.
- **상여 등 지급 건 유형이 다른 경우**: 같은 구성으로 그 지급 건의 값만 보여준다(기재사항은 대개 없음).
- **같은 달에 지급 건이 여러 개**(정기급여+상여): 지금처럼 어떤 건인지 고르게 하거나 질문에 맞는 건을 쓴다. 두 건을 한 명세서로 합치지 않는다.
- **다른 직원의 명세서 요청**: 기존처럼 거절한다(본인 사번 강제, 다른 직원 거절 규칙 유지).
- **금액/시간등 값**: 5240이 포맷한 문자열(시간·금액)을 그대로 보여준다. 숫자로 다시 계산하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: "급여명세서/페이슬립/월급 명세서"처럼 특정 지급 건의 명세 전체를 묻는 질문에는 합계·지급내역·공제내역·기재사항을 한 답에 담아야 한다(D1).
- **FR-002**: 합계는 5240이 주는 지급금액·공제금액·실지급액 값을 그대로 보여야 한다. 지급·공제 표의 합으로 다시 계산해 바꾸지 않는다.
- **FR-003**: 지급내역 표는 지급항목·지급금액과 합계 줄을 보여야 하고, 소급금액은 그 지급 건의 소급금액 합이 0이 아닐 때만 칸으로 보여야 한다(D4).
- **FR-004**: 공제내역 표는 공제항목·공제금액과 합계 줄을 보여야 한다.
- **FR-005**: 기재사항 표는 기재구분(E=기준항목, T=근태항목)·기재항목·금액/시간등을 보여야 하고, 행이 없으면 표를 생략해야 한다(D6).
- **FR-006**: 어느 표에도 지급구분·급여연월(적용년월) 칸을 보이지 않아야 한다(D4).
- **FR-007**: 고지사항은 보이지 않아야 한다(D5).
- **FR-008**: 한 영역의 조회가 실패하면 그 영역만 실패로 표시하고 나머지 영역을 보여야 한다. 실패한 영역의 값을 지어내지 않는다(D7).
- **FR-009**: 공제만·실수령만 묻는 질문은 지금처럼 해당 영역만 답해야 한다(D2).
- **FR-010**: 이번 달 미지급 시 지난달 건으로 보여주는 기존 규칙이 새 구성에서도 같게 동작해야 한다(D9).
- **FR-011**: 위젯 브리지는 기재사항 조회를 허용해야 하고, 그 조회의 사번은 기존 급여명세 조회와 같이 본인으로 강제해야 한다(D8). 다른 새 조회는 허용하지 않는다.
- **FR-012**: 급여 질문의 조회 선택(어떤 질문이 명세서·공제·실수령으로 가는지)을 라우팅 평가 케이스와 E2E 시나리오로 검증해야 한다(Convention §7.3, E2E-First).
- **FR-013**: 날짜는 하이픈 형식, 금액 칸에 막대 없음(D10)을 유지해야 한다.

### Key Entities

- **지급 건**: 급여일자+지급 유형(정기급여·상여 등)으로 정해지는 한 번의 급여 지급. 명세서의 단위.
- **합계**: 지급 건의 지급금액·공제금액·실지급액(5240 정본 값).
- **지급 항목**: 지급항목명·지급금액·소급금액.
- **공제 항목**: 공제항목명·공제금액.
- **기재 항목**: 기재구분(기준항목/근태항목)·기재항목명·금액/시간등(5240이 포맷한 문자열).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 가짜 지급 건(지급 4·공제 6·기재 2)으로 명세서를 물었을 때, 10회 중 10회 모두 네 영역이 D3 순서로 나오고 금액이 5240 응답과 1원도 다르지 않다.
- **SC-002**: 명세서 답의 어느 표에도 지급구분·급여연월 칸이 나오지 않는다(10회 중 0회).
- **SC-003**: "얼마 떼갔어?"·"실수령 얼마야?" 질문은 10회 중 10회 해당 영역만 나온다(명세서 전체가 나오는 경우 0회).
- **SC-004**: 급여 라우팅 평가 케이스(명세서·공제·실수령·지급 건 목록)가 수정 전보다 떨어지지 않고, 하네스 전체가 기존 알려진 실패 외 새 실패 없이 2회 연속 통과한다.
- **SC-005**: 기재사항 조회가 막힌 상태에서도 명세서 답이 나머지 세 영역을 보여준다(실패 표시 포함).

## Assumptions

- 기재사항 조회는 기존 급여명세 조회와 같은 경로·같은 지급 건 코드·같은 본인 사번 파라미터를 받는다(kiwibox SQL `getSALSalaryDtstmnMgrList3`, 2026-11-18 확인). 응답 칸은 기재항목명(SAL_ITEM_NM)·기재구분 코드(SAL_ENTR_CD)·금액(SAL_AMT, 5240이 포맷한 문자열)이다.
- 테스트 계정(오이사공 고객관리팀)은 실제 급여 데이터가 없어, 검증은 가짜 응답(로컬)과 E2E mock fixture로 한다. 응답 래퍼 모양은 같은 경로의 실측(`{"Message":"","DATA":[...]}`, 합계는 단건 객체)을 따른다.
- 운영 반영에는 TeamplGPT 배포와 okrservice 위젯 배포가 모두 필요하다. 위젯이 먼저 배포되지 않으면 기재사항만 실패로 표시된다(Edge Cases).
- 위젯 폭에서 지급·공제 표는 칸이 2~3개라 옆으로 밀지 않고 보인다. 합계 표는 3칸.
- 고지사항, 급여분석 탭(5240 화면의 다른 탭)은 이번 범위 밖이다.
